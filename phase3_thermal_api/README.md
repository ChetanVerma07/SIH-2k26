# Phase 3 — Passive Shelter Thermal Simulation API

A standalone, physics-based (no AI/ML) transient thermal calculation engine
for passive shelter design analysis, exposed over a REST API built with
FastAPI. This is **Phase 3** of a larger SIH 2026 project and is built as a
completely independent service:

- No frontend code
- No database
- No ANSYS dependency
- No external weather APIs
- Clean JSON API that a separate frontend can call later

---

## 6. Request / Response Shape

### Climate input (two modes)

**Mode 1 — constant:**

```json
{"ambient_temperature": -10, "solar_radiation": 500}
```

**Mode 2 — time series** (list of points, `time` in hours from the start of
the simulation; values in between supplied timestamps are linearly
interpolated to the simulation's own time step):

```json
[
  {"time": 0, "ambient_temperature": -10, "solar_radiation": 0},
  {"time": 1, "ambient_temperature": -10, "solar_radiation": 100}
]
```

Both modes accept an optional `ground_temperature` field (defaults to
`ambient_temperature` if omitted — see Section 8, Limitations).

### Shelter configuration

```json
{
  "name": "My Shelter",
  "length": 6.0,
  "width": 4.0,
  "height": 2.7,
  "orientation": "S",
  "wall_material": { "...": "Material object, or a list of Material layers" },
  "roof_material": { "...": "Material object, or a list of Material layers" },
  "floor_material": { "...": "Material object, or a list of Material layers" },
  "openings": {
    "window_area": 4.0,
    "door_area": 2.0,
    "other_opening_area": 0.5,
    "opening_u_value": 2.8,
    "window_shgc": 0.65
  },
  "structural_mass_fraction": 0.35
}
```

`wall_material` / `roof_material` / `floor_material` each accept either a
single `Material` object or an **ordered list** of `Material` layers
(e.g. structural layer + insulation layer), letting you model layered
construction.

## 7. Thermal Model — Equations Used

All units are SI unless stated (temperatures in °C are used directly as
temperature *differences*, which are numerically identical to Kelvin
differences).

### 7.1 Conduction (walls, roof, floor, openings)

For each building element:

```
R_layer  = thickness / thermal_conductivity        (m^2*K / W)
R_total  = sum(R_layer for each layer in assembly) (layers in series)
U        = 1 / R_total                             (W / m^2*K)
Q        = U * A * dT
```

- **Walls:** `dT = T_indoor - T_ambient`, `A` = net wall area (gross wall
  area minus total opening area, so openings are never double-counted).
- **Roof:** `dT = T_indoor - T_ambient`, `A` = footprint area (`length * width`).
- **Floor:** `dT = T_indoor - T_ground`, `A` = footprint area. The floor
  exchanges heat with a `ground_temperature` rather than open-air ambient
  temperature, since floors are typically in contact with the ground/slab
  rather than exposed air.
- **Openings** (windows + doors + other): `dT = T_indoor - T_ambient`,
  `A` = total opening area, `U` = the single `opening_u_value` supplied in
  the request (openings are not modeled as material layers, since window
  frames/glazing/seals behave very differently from opaque wall
  construction).

### 7.2 Solar gain

```
Q_solar = Solar_Radiation * Effective_Area * Solar_Absorptivity
```

Applied to three separate surfaces (see Section 9, Orientation):

1. **Roof:** always fully exposed —
   `Q_roof = SolarRadiation * RoofArea * RoofAbsorptivity`.
2. **Front (orientation-facing) opaque wall area:**
   `Q_wall = SolarRadiation * OrientationFactor * OpaqueFrontArea * WallAbsorptivity`.
3. **Front-facing windows** (transmitted, not absorbed, so uses SHGC
   instead of absorptivity):
   `Q_window = SolarRadiation * OrientationFactor * FrontWindowArea * WindowSHGC`.

Total: `Q_solar = Q_roof + Q_wall + Q_window`.

### 7.3 Net heat flow

```
Q_net = Q_solar - (Q_wall_loss + Q_roof_loss + Q_floor_loss + Q_opening_loss)
```

### 7.4 Transient indoor temperature update

The shelter's indoor air is modeled as a single lumped thermal-capacitance
node (an RC "1R1C"-style simplification):

```
C_total = C_air + structural_mass_fraction * C_structure

T_indoor(t + dt) = T_indoor(t) + (dt_seconds / C_total) * Q_net(t)
```

where:

- `C_air = air_density * air_specific_heat * shelter_volume`
  (using standard air properties: 1.2 kg/m³, 1005 J/(kg·K)).
- `C_structure` = sum of each element's areal heat capacity
  (`density * specific_heat * thickness`) times its area, for walls, roof,
  and floor, scaled by the user-supplied `structural_mass_fraction`
  (default 0.3) — the fraction of the structure's thermal mass assumed to
  respond closely enough to indoor conditions within a timestep to matter
  for the indoor-air balance.
- Integration is explicit (forward) Euler: each step's indoor temperature
  depends on the *previous* step's temperature and heat flows, which is
  what makes the model genuinely transient rather than a series of
  independent steady-state snapshots.

This is the physics implemented in `app/thermal/` — `conduction.py`,
`solar.py`, `heat_balance.py`, and `simulator.py`.

## 9. Orientation — Documented Assumption

The shelter is treated as a rectangular box with a single "front" facade
(area = `width * height`) assumed to face the compass direction given by
`orientation`. That facade's solar exposure is scaled by a fixed
orientation factor:

| Orientation | Factor |
|-------------|--------|
| S           | 1.00   |
| SE / SW     | 0.85   |
| E / W       | 0.60   |
| NE / NW     | 0.40   |
| N           | 0.20   |

The roof always receives the full supplied `solar_radiation` value (it
faces the sky). Openings (windows) are assumed to be evenly distributed
across all four facades, so only one quarter of the total window area is
treated as facing the sun.

**This is a simplified, time-invariant exposure model — not a full
solar-geometry / sun-path engine.** It does not account for solar
altitude, azimuth, shading, or the sun moving across the sky through the
day. A complete solar-geometry model is out of scope for Phase 3 and
would be a natural extension.

## 10. Limitations — What Is Simplified

This is a **prototype-grade, physically-motivated engineering model**, not
a certified simulation tool. It is intended to support rapid design
comparison and iteration, not final design sign-off. Specifically:

- **Single-node (lumped capacitance) indoor air model.** Real buildings
  have distinct wall-surface, wall-core, and air-node temperatures; this
  model collapses them into one indoor temperature, with structural mass
  coupled in through a single `structural_mass_fraction` knob rather than
  a full multi-node RC network.
- **No convection coefficients.** Heat transfer coefficients are folded
  into the material `U`-values and the fixed `opening_u_value`, rather
  than computed from wind speed, indoor/outdoor air movement, or surface
  orientation.
- **No infiltration/ventilation air-change model.** Air leakage through
  cracks and gaps (distinct from explicit window/door openings) is not
  modeled.
- **No long-wave (thermal) radiation exchange.** `emissivity` is captured
  on the `Material` model for future extension but is not yet used in the
  heat balance (no sky/night radiative cooling term).
- **Simplified orientation/solar-geometry model** (see Section 9) — no
  solar altitude/azimuth, shading, or reflected/diffuse radiation
  decomposition.
- **Explicit (forward) Euler integration.** This is conditionally stable;
  `time_step_minutes` is capped at 120 minutes in `SimulationSettings` to
  stay well within the stable region for realistic shelter thermal
  masses. Very large time steps combined with very low thermal mass could
  still be numerically stiff in unusual configurations.
- **Ground temperature is a simplification.** If not explicitly supplied,
  it defaults to ambient air temperature, which is a rough approximation
  — real ground temperature lags and dampens air temperature swings.
- **No human/equipment internal heat gains** (occupants, appliances,
  lighting) are modeled — only envelope conduction and solar gain.
- **Energy totals use simple rectangular integration** (each instantaneous
  power sample held constant for one `time_step_minutes` interval), not
  trapezoidal integration — a minor approximation that shrinks as the time
  step gets smaller.

### What requires ANSYS validation

This model does **not** claim equivalence to a full computational
thermal/CFD simulation such as ANSYS. Before relying on results for a real
build, the following should be validated against a detailed
finite-element/CFD thermal model (a later project phase):

- Multi-node transient conduction through actual wall/roof/floor
  assemblies (this model only computes a single lumped U-value per
  assembly).
- Convective heat transfer coefficients under real wind/airflow
  conditions.
- Detailed solar-geometry and shading analysis.
- Infiltration and mechanical/natural ventilation airflow.
- Long-wave radiation exchange (including night-sky radiative cooling,
  which matters a great deal in high-altitude cold-desert climates like
  Ladakh).

ANSYS integration is explicitly **out of scope for Phase 3** and is
planned as a separate, later component of the overall project.

## 11. Architecture

```
phase3_thermal_api/
│
├── app/
│   ├── main.py                    # FastAPI app + endpoint definitions
│   ├── models/                    # Pydantic request/response/domain models
│   │   ├── climate.py             # ConstantClimate, ClimatePoint
│   │   ├── material.py            # Material + layered-assembly helpers
│   │   ├── shelter.py             # ShelterConfig, OpeningProperties, Orientation
│   │   └── simulation.py          # Settings, requests, and result models
│   ├── thermal/                   # Pure physics — no FastAPI/HTTP concerns
│   │   ├── conduction.py          # Q = U * A * dT
│   │   ├── solar.py               # Q_solar = Radiation * Area * Absorptivity/SHGC
│   │   ├── heat_balance.py        # Combines all Q terms; thermal mass
│   │   └── simulator.py           # Climate interpolation + transient time-stepping
│   ├── services/                  # Orchestration between API and physics
│   │   ├── simulation_service.py  # Runs one simulation, builds SimulationResult
│   │   └── comparison_service.py  # Runs + ranks multiple shelter designs
│   └── data/
│       └── materials.py           # Example material library
│
├── tests/                         # Pytest suite (API-level + unit-level)
├── examples/                      # Example request payloads (Ladakh scenario, compare)
├── requirements.txt
├── Dockerfile
└── README.md                      # This file
```

**Design principles:**

- `app/thermal/` contains *only* physics functions — no Pydantic, no
  FastAPI, no HTTP — so the calculation engine can be reused, unit-tested,
  or even embedded elsewhere independently of the web layer.
- `app/models/` is the single source of truth for validation rules
  (dimension positivity, comfort-range ordering, opening-area-vs-wall-area
  checks, etc.), enforced automatically by Pydantic and surfaced as
  HTTP 422 responses.
- `app/services/` is a thin orchestration layer that turns validated
  request models into raw simulation output and back into response
  models — this is where per-endpoint business logic (like the ranking
  algorithm in `comparison_service.py`) lives.

## 12. Design Comparison Ranking

`/api/compare` computes, for each shelter design, min-max-normalized
scores for three criteria and combines them with configurable weights
(default `{"comfort": 0.5, "heat_loss": 0.3, "solar_gain": 0.2}`):

```
score = w_comfort   * normalized(comfort_percentage)
      + w_heat_loss  * normalized(-total_heat_loss)      # lower loss -> higher score
      + w_solar_gain * normalized(total_solar_energy_gained)
```

Designs are then sorted in descending score order and assigned integer
ranks. This is a transparent, deterministic weighted-scoring method — no
machine learning is used for ranking in this phase.
